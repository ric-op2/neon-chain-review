# AB両面・複数ステージ・ハイスコア保存の設計案

2026-09-10 · 検討用。v0.40で実装したのは旋回中間でのキューブ表示のみです。複数曲、ディスク保存、以下の画面遷移はまだゲーム本体へ実装していません。

## 搭載曲数の見通し

**標準的な長さの曲を想定した初期目標は12〜16ステージ。今回の基準データなら、A面3曲＋B面13曲＝16ステージが容量上収まる計算です。** 1曲につきEASY/HARDを用意しますが、難易度ごとに曲数を数えません。

これは「変換後の曲がゲーム用メモリに収まる設計へ改修できた場合」の見積もりです。今のゲームは1ステージで、ディスクを両面にするだけでは増やせません。任意NSFのサイズや音源は一定でないため、どの16曲でも入る保証はありません。

| 音楽データ／曲 | 音楽＋EASY/HARD譜面など／ステージ | A面 | B面 | 合計（容量上） |
|---|---|---|---|---|
| 1,536バイト・軽量な例 | 2,407バイト | 6曲 | 24曲 | 30曲 |
| **3,433バイト・自作曲120秒の変換実測** | **4,304バイト** | **3曲** | **13曲** | **16曲** |
| 6,144バイト・重い例 | 7,015バイト | 2曲 | 8曲 | 10曲 |
| 10,240バイト・さらに重い例 | 11,111バイト | 1曲 | 5曲 | 6曲 |

3,433バイトは1曲の実測値であり、任意NSFの平均ではありません。重い例はディスク容量だけの試算で、より大きな曲用RAM領域も必要です。長い曲、DPCM、特殊な音源操作、密な譜面は容量を増やします。

### 計算の前提

- `.fds`は1面65,500バイト、AB両面ならヘッダー込み131,016バイトです。[FDSファイル形式](https://www.nesdev.org/wiki/FDS_file_format)
- 計画上は各面60,000バイトまで使用し、5,500バイトずつ余裕を取ります。これは設計上の仮置きで、実ディスクの保証値ではありません。`.fds`に含まれないギャップ・CRCもあるため、実機で書き込みと全ファイル読み込みを確認します。
- 現在のA面相当の起動ファイル群は41,343バイト。ここにメニュー用2,048、カタログ512、セーブ1,024バイトとファイル管理分を追加します。
- 1ステージは音楽＋EASY/HARD各118イベント×3バイト＋予告18＋情報128＋ファイル管理17バイトと仮定します。音声のPCMやNSFプレーヤー自体を曲ごとに重複保存する想定ではありません。
- A面の固定分44,978、B面の固定分1,628バイト。基準ケースはA面57,890、B面57,580バイトになります。
- 現在の起動ファイルに含まれる元の曲を除去した場合の削減は、見積もりに加えていません。新しいメニューや読み込み処理の増加量は実装後に再計測します。

## 推奨するAB面のファイル配置

| 面・順序 | ファイル案 | 役割 |
|---|---|---|
| A・先頭 | NEONCODE | 共通ゲームコード、共通描画データ、音楽ドライバーを起動時に読み込む。 |
| A | NEONART | 共通CHR画像。曲ごとに重複させない。 |
| A | BOOTNMI / BOOTWAIT | 現在の起動方式を維持。実在するファイル数を宣言する。 |
| A | MENUCORE | タイトル、曲選択、結果画面の処理。2KiBは仮のディスク容量枠。常駐・共有方式はRAM設計時に決める。 |
| A | CATALOG | 全16曲の識別子、所在面、難易度、長さなど。 |
| A | STG000〜STG002 | A面の3ステージ。選択した1曲だけRAMへ読み込む。 |
| **A・最後** | **SCORE_A** | **A面の曲の記録。固定長1KiB。** |
| B・先頭 | CATALOG | 同じ曲リストとビルド識別情報。 |
| B | STG003〜STG015 | B面の13ステージ。 |
| **B・最後** | **SCORE_B** | **B面の曲の記録。固定長1KiB。** |

**セーブファイルの後ろに曲や画像を置かないことが重要です。** BIOSのWriteFileで途中のファイルを更新すると、後続ファイルが論理的に隠れるためです。[BIOSの書き込み仕様](https://www.nesdev.org/wiki/FDS_BIOS)

読み込み用のFile IDと、書き込み時の通し番号を混同しない設計にします。案ではステージIDを`$20〜$2F`、セーブIDを各面`$7E`とし、セーブ時の通し番号は面ごとの最後の番号をビルド時に生成します。B面単独からのコールドブートは想定せず、A面で起動して共通プログラムをRAMに残したまま面を替えます。[ディスク構造](https://www.nesdev.org/wiki/FDS_disk_format)

### ディスク交換を減らす動作

同じ面の曲を続けて遊ぶ間は面交換不要とします。別の面の曲を選んだときだけ交換を案内します。記録も現在の面へ保存するため、クリアのたびにA面へ戻す必要はありません。

起動時はA面の記録を読み込みます。B面の記録は最初にB面を入れたときに読み込み、以後RAMに保持します。未読の記録は「未読」と表示し、0点として扱いません。全曲の記録をすぐ閲覧したい場合は、一度B面の読み込みを案内します。

代案として、A面を起動専用、B面を全曲＋全記録にすると、起動後に一度裏返すだけで済みます。ただし、同じ容量仮定ではB面13曲程度となり、A面の余剰領域を曲に使う16曲案より少なくなります。

## ハイスコア保存

**ディスク書き込みによる保存は実現可能です。** 曲・難易度・通常／RANDOMごとの自己ベストを保存する案です。初期仕様は各条件の1位のみとし、上位3件やプレイヤー名は後から検討します。

| 保存項目 | 案 |
|---|---|
| ファイル | 各面の最後に固定長1,024バイトを最初から確保。 |
| ヘッダー | 形式番号、面、曲数、ビルド／曲パック識別子、更新番号、チェックサム。 |
| ステージ識別 | 曲IDと譜面改訂番号。曲順を変えても別曲の記録と混ざらないようにする。 |
| 条件 | EASY/HARD × 通常/RANDOMの4条件。RANDOMは通常記録と分離。 |
| 条件ごとの記録 | スコア3バイト、最大チェイン2、達成フラグ1、精度2の計8バイト。 |
| 容量例 | ヘッダー32＋13曲×（曲ID等6＋4条件×8）＝526バイト。1KiBに収まる。 |

保存スコアを24ビットにしても、現ゲームのスコア計算は16ビットなので、その拡張は別途必要です。RANDOMの同一配置別ランキングや入力履歴の保存は、この容量に含めていません。

### 保存するタイミングと失敗時の動作

クリア後に記録を比較し、更新があれば結果画面で保存します。更新がない場合は書き込みません。保存後は「曲選択へ」「もう一度プレイ」を選べます。失敗終了時のスコアを登録するかは追加仕様ですが、画面遷移自体は結果画面へ統一できます。

保存中は演奏とラスタ割り込みを止め、ディスクI/O用状態に切り替えます。BIOSが使うゼロページと制御情報を保護・復元し、書き込み完了と読み戻しを確認してから「保存済み」にします。今のプログラムは独自IRQとゼロページを使っているため、BIOSを単に呼び足すだけでは済みません。[BIOSとのRAM共有](https://www.nesdev.org/wiki/User%3ATakuikaNinja/Programming_the_FDS)

書き込み禁止・別面・未挿入・検証失敗では「再試行」「保存せず続ける」を表示し、RAM上の新記録は保持します。既存セーブを読めていないときは、そのまま初期値で上書きしません。チェックサム不一致は検出できますが、同じファイル内の二重記録だけでは書き込み途中の電源断からの復旧は保証できません。

FDSKeyは保存方式を選択できます。ただし、ゲーム側の書き込み完了とSDへの反映完了には区別があるため、実機・FDSKey・エミュレーターで、終了後に再起動して記録が残ることまで確認します。[FDSKeyの保存仕様](https://github.com/ClusterM/fdskey)

## 画面遷移

**タイトル → 曲選択（PLAY／RECORDS切替） → 曲・難易度決定 → 必要なら面交換と読み込み → プレイ → 結果・記録保存 → 曲選択へ／もう一度プレイ**

| 画面 | 操作・表示案 |
|---|---|
| タイトル | STARTで曲選択。デモ曲の演奏は任意。 |
| 曲選択・PLAY | 上下で曲、左右でPLAY/RECORDS、SELECTで難易度、Aで決定、Bでタイトル。曲名・所在面・難易度・自己ベストを表示。RANDOMは独立した設定項目にする。 |
| 曲選択・RECORDS | 同じ曲カーソルで記録を閲覧。未読の面は読み込みを案内。BでPLAYへ。 |
| 面交換／読み込み | 「B面を入れてください」等を表示。曲パックと面を確認してから読み込み、成功後にカウントダウンへ。キャンセルで曲選択へ戻る。 |
| プレイ | 現在の操作を維持。演奏中のディスクアクセスは行わない。 |
| 結果 | スコア、自己ベスト更新、保存状態を表示。保存完了または保存を見送った後に行き先を選ぶ。 |
| もう一度プレイ | 同じ曲・難易度でもう一度遊ぶ。RANDOMは同じシードを保持する案。曲データがRAMに残っていれば再読み込み不要。 |

ここでの「リプレイ」は録画や入力履歴の鑑賞ではなく、同じ曲の再プレイとして設計しています。曲選択からは曲と難易度を保持して戻り、毎回先頭曲へ戻さないようにします。

## 最大の課題はRAMと共通コード

AB面にしても、実行用の32KiB PRG-RAMは増えません。現v0.40のCODE/RODATA末尾は`$DD94`で、`$DF00`までの余白は363バイト。BSSの余りも19バイトです。

曲ごとの読み込みには、まず音楽＋譜面用に4〜6KiB程度の入れ替え領域を確保する必要があります。16曲×4条件の記録キャッシュは512バイト、書き込み用1KiBと合わせ約1.5KiBの作業領域も検討対象です。これらは今の余白には入りません。

共通描画データの削減、曲データの分離、画面別に使う作業領域の共有、メニューとプレイ処理の常駐範囲の整理が必要です。特に今の絵の展開データは既に圧縮されているため、大幅削減を未検証のまま約束できません。BIOSとの割り込み・メモリ共有を解決し、1曲を読み替えて正常に遊べるところまで作った後に搭載曲数を確定します。

任意NSFをそのまま実行する方式ではなく、対応音源の曲をゲーム用へ変換・最適化する方式が前提です。追加音源、DPCM、大きい曲は別判定とし、AB容量に収まっても実行できない場合があります。

## 実装するなら、この順序

1. 現曲ともう1曲で、曲データの入れ替え・音楽同期・メモリ余裕を確認する。
2. AB面のカタログ、面交換、曲選択と結果画面を実装する。
3. 各面最後の1KiBセーブを実装し、再起動後の復元とエラー時の動作を確認する。
4. 実際の収録候補を変換し、まず12曲、余裕を測って16曲へ拡張する。

検証項目は、別面の誤挿入、書き込み禁止、セーブ読取失敗、ゲーム終了後の再起動、曲パック更新、再プレイの再初期化、全曲のEASY/HARD完走です。搭載予定の曲数を増やす前に、共通の読み込み・保存経路を固めます。
